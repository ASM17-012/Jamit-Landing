# 앱 화면 녹화

`/next/` 가 쓰는 앱 화면 영상이다. 전부 **실제 JamIT-iOS 앱을 화면 녹화**한 것이고,
그린 목업은 한 장도 없다. 여기 규격을 지켜야 `next/index.html` 의 기기 칸에 그대로 맞는다.

## 무엇을 찍나

파일명은 `next/index.html` 의 `data-src` 와 1:1이다. 이름을 바꾸면 그쪽도 같이 고쳐야 한다.
장 구성과 문구는 앱스토어 스크린샷 여덟 장에서 왔고, 순서만 사용자 여정에 맞게 바꿨다.

히어로는 화면 크기에 따라 다른 것을 세운다.

| 파일 | 어디에 | 무엇 |
|---|---|---|
| `hero-its.mp4` | 데스크톱 히어로 (한 대, 3D 기울임) | 여러 연주가 한 화면에서 함께 도는 잇츠 (`원본 잇츠 앞 부분.mp4` 앞 8초) |
| `tour-home.jpg` | 휴대폰 히어로 | 앱 홈 화면 — 글 아래에 서서 화면 끝에 걸친다 |

**히어로는 목업 두 대다.** 왼쪽 뒤가 「혼자 녹화한 연주」, 오른쪽 앞이 「그것이 합주가
된 잇츠」 — 제목 「나만의 연주가 우리의 합주로」가 그대로 화면 둘이다.

한때 CSS 로 기울인 두 대를 세웠다가 한 대로 줄인 적이 있는데, 그때 문제는 **나란히
서면 기울기를 ±5° 밖에 못 준다**는 것이었다(233×505 를 14° 돌리면 가로 상자가 348px
로 부풀어 옆엣것과 부딪는다). 렌더 목업은 기울기가 그림에 이미 들어 있어 상자가
부풀지 않는다 — 그래서 두 대가 다시 선다.

- 크기를 벌린다: 앞엣것 칸의 58%, 뒤엣것 48%. 같은 크기로 두면 둘 중 어디를
  봐야 할지 갈린다.
- **위아래로 엇갈려 세운다** — 앞엣것(잇츠)은 위로, 뒤엣것(녹화)은 14% 아래로.
  그래야 좌우로 더 겹칠 수 있다: 기울어 있어 상자 모서리가 비어 있는 데다 세로로
  어긋나 있어서, 상자를 6% 겹쳐도 몸통 사이에는 여전히 틈이 보인다.
  나란히(엇갈림 없이) 두면 같은 폭에서 기기가 389px 인데, 엇갈리면 418px 이다.
- 히어로 장만 위아래 여백을 줄였다(`clamp(40px,6.6vh,80px)`) — 엇갈린 두 대가
  세로를 더 쓴다. 1440 화면에서 쓸 수 있는 높이가 702 → 780px 이 된다.
- 기기를 키우려고 **히어로만 오른쪽으로 더 뻗는다.** 왼쪽은 페이지 격자에 그대로
  맞추고(가운데 정렬로 넓히면 제목 왼쪽 끝이 아래 장들과 어긋난다) 오른쪽만
  화면 끝에서 24px 남긴다.
- **글 칸은 제목 줄을 실제로 재서 잡았다** — 1440 에서 530px, 1728 에서 561px,
  880 에서 330px. 눈대중으로 617 로 잡고 있었는데 그만큼 기기 칸을 헛으로 비워
  두고 있었다. 줄지 않는 고정 폭이어야 한다(minmax 로 두면 기기에 밀려 줄어들고
  제목이 네 줄로 깨진다).

```
1440 화면   잇츠 292 → 418px · 녹화 216 → 346px
1728 화면   잇츠 429px · 녹화 355px
 880 화면   잇츠 237px · 녹화 196px
```
- **한쪽만 움직인다.** 움직이는 쪽은 잇츠다 — 이 앱이 만들어 내는 결과가 그것이고,
  정지 화면으로는 「여러 연주가 한 화면에서 같이 돈다」가 읽히지 않는다.
  녹화 쪽은 손이 줄 위에 있는 한 프레임이면 충분하다.
- 목업 둘은 **서로 다른 방향으로 기울어 있다**(검정은 시계 방향, 파랑은 반시계).
  마주 보게 두면 둘이 한 짝으로 읽힌다.

### 히어로에서 다음 장으로 넘어가는 자리에는 전환을 두지 않는다

여기에 지니를 만들어 봤다가 뺐다 — 히어로의 녹화 화면이 프레임에서 빠져나와
다음 장의 녹화 화면으로 빨려 들어가는 것이었는데, 세 가지가 걸렸다.

- **목적지가 가만있지 않는다.** 날아가는 동안 다음 장의 기기도 같이 올라온다
  (실측: 280px 스크롤 구간에 목적지가 280px 이동). 딱 들어맞는 순간이 없다.
  아래 지니(녹화 → 트랙 카드)가 되는 이유는 출발지와 목적지가 **같은 붙박이 기기
  안**이어서다 — 그 안에서는 목적지가 못 박혀 있다.
- **모양이 다르다.** 날아가는 것은 3D 목업에서 떼어낸 기울어진 사각형이고 도착지는
  반듯한 화면이라, 도착 직전에 흐려서 숨길 수밖에 없었다.
  **가리지 않으면 안 되는 전환은 좋은 전환이 아니다.**
- **새로 알려 주는 것이 없다.** 다음 장 첫 마디가 어차피 그 녹화 화면이고,
  스크롤하면 저절로 나타난다.

이 페이지의 전환 넷(지니 · 확대 · 잇츠 넘김 · 탭 크로스페이드)은 모두 **그 움직임
자체가 내용인 자리**에 있다 — 「방금 찍은 것이 저 카드에 들어갔다」, 「편집 창에서
잇츠가 자라 나온다」, 「스크롤하면 다음 잇츠로 넘어간다」, 「탭을 옮기면 화면이
바뀐다」. 히어로 이음매에는 그런 것이 없어서 비워 둔다.

휴대폰도 같다. 거기 첫 화면은 글이 먼저 오고 앱 화면이 화면 끝에 걸치는 정지 화면이라,
바로 뒤에 전환을 하나 더 넣으면 서로 잡아먹는다. 게다가 히어로 기기(215px)와 다음 장
기기(290px)는 크기가 35% 차이 나고, 담긴 화면도 다르다(홈 화면 대 녹화 화면).

### 기기 = 3D 렌더 목업 그림 (`frame.png`)

테를 CSS 로 칠해도 봤지만(사선 금속 그러데이션 + 버튼 + 그림자) 거기까지였다.
**옆면의 두께는 면 하나를 눕혀서는 그릴 수 없다.** 그래서 렌더 목업 그림을 얹고
그 화면 구멍에 영상을 물린다 — 기울기와 두께, 빛까지 그림이 다 가지고 있다.

받은 파일은 흰 바탕 JPG(626×545)라 **알파가 없었다.** 다음 순서로 뚫는다.

1. 바깥(흰 바탕)과 화면(순백)에서 각각 **범람 채우기**로 영역을 잡아 알파 0 으로.
   전역 색 키잉을 쓰면 기기의 밝은 부분까지 같이 날아간다. 둘은 검은 테가
   막고 있어 서로 새지 않는다(실측: 바깥 221,426px · 화면 97,528px).
2. 불투명 덩어리 중 **가장 큰 것만** 남겨 얼룩을 없앤다.
3. **가장자리 알파를 되돌린다(매팅).** 이걸 안 하면 기기 윤곽에 흰 실선이 남는다 —
   JPEG 의 경계 픽셀은 기기 색과 흰 배경이 섞인 회색인데, 잘라내기만 하면 그 회색이
   불투명하게 남기 때문이다. 흰색과의 혼합으로 보고 되돌린다:

   ```
   C = αF + (1-α)·255   →   α = (255 - lum(C)) / (255 - lum(F))
   ```

   F(진짜 기기 색)는 2px 안쪽의 오염되지 않은 이웃 중 **가장 어두운 것**으로 잡고,
   그 색으로 덮어쓴다. 두 겹(3,309px + 65px)을 이렇게 다듬으면 윤곽이 배경에
   부드럽게 붙는다. 한 겹만 지우는 방식으로는 계단이 생긴다.
4. RGB 를 8단계로 양자화하고, **기기 상자에 맞춰 자른다**(x 179~505, y 7~527 →
   여백 6px 을 두고 338×532). 빈 여백을 남기면 같은 칸에서 기기가 그만큼 작게
   그려진다. 결과 **30KB**.

### 구멍에 영상을 물리는 법

알파에서 구멍의 네 변을 최소제곱으로 맞추고 교차시켜 꼭짓점을 얻는다.

- **윗변을 잴 때는 노치가 걸친 열(x 356~425)을 뺀다.** 노치 아래쪽이 화면 경계로
  잡혀 윗변이 10px 내려앉고, 그만큼 영상 위에 흰 띠가 남았다.
- **노치는 지웠다.** 목업은 노치 세대 기기인데 녹화는 다이내믹 아일랜드 세대(16 Pro)라,
  노치를 얹으면 화면 위에 검은 혹이 하나 더 생긴다. 구멍(사각형) **안쪽에서만**
  범람 채우기를 돌려 985px 을 투명하게 만들면, 그 자리에 녹화가 가진 진짜
  아일랜드가 드러난다. 검은 테와 노치가 같은 색이라 색만으로는 못 가른다 —
  구멍 안이라는 조건이 경계 역할을 한다.
- 위 변 200.3 / 아래 변 205.3 — 아래가 5px 넓다. **진짜 원근이 있다**는 뜻이다.
  어파인(matrix)으로 근사하면 네 번째 꼭짓점이 9px 어긋나는데 왼쪽 테가 8px
  뿐이라 영상이 기기 밖으로 샌다. 그래서 네 점을 정확히 맞추는
  **사영변환(matrix3d)** 을 푼다 — 검산 오차 0.00px.
- 넓힐 때는 **네 변을 각각 2.5px 바깥으로 민 뒤 다시 교차**시킨다. 중심에서
  방사로 키우면 세로로 긴 사각형은 위아래로만 커지고 좌우는 그대로라, 왼쪽
  가장자리에 흰 실선이 남는다.

```css
.mock{aspect-ratio:338/532}
.mock__scr{width:230.94px;height:502.10px;transform-origin:0 0;border-radius:11px;
  transform:scale(var(--s,1))
    matrix3d(.841749,-.039014,0,-.00014803,-.215135,.920743,0,-.00007882,0,0,1,0,114.079,20.183,0,1)}
```

matrix3d 의 원근 항(m14·m24)은 **길이의 역수**라 크기가 바뀌면 같이 바뀌어야 한다.
그래서 영상 칸만 고정 px(그림 좌표계)로 두고, 목업이 실제로 그려진 폭에 맞춘 배율
하나를 스크립트가 `--s` 로 준다 — `scale(s)∘H` 는 `H` 의 결과를 s 배 한 것과 같다.
(평행사변형이면 이 항이 0 이라 `translate(%)` 로 자바스크립트 없이 끝난다.
앞서 쓴 은색 목업이 그랬다.)

휴대폰에서는 이 판이 통째로 감춰지지만 **감춰도 그림은 받는다** — 그쪽에는
`<picture><source media>` 로 빈 그림을 줘서 요청이 아예 나가지 않게 한다.

**이 파일의 한계** — 626×545 짜리 스톡 미리보기다. 목업 칸이 420px 이면 기기가
405px 로 그려지는데 원본이 326px 뿐이라 1.24배 확대된다(배율 2 화면에서는 더).
그리고 스톡 미리보기는 보통 그대로 쓸 수 있는 파일이 아니다. 공개 전에 **투명 PNG
원본(1400px 이상)** 을 받아 같은 자리에 덮으면 된다 — 구멍 재는 법은 위에 그대로 있다.

```
첫 화면   데스크톱 2083KB (다음 장 record.mp4 1064 + 목업 둘 88 + 녹화 사진 76 포함) · 휴대폰 539KB
```

## 어디서 찍나 — 실기기다

시뮬레이터로 찍으면 안 되는 화면이 있다. `RecordCameraScreen` 은 카메라를 쓰는데
시뮬레이터에는 카메라가 없어 검은 화면이 나온다. 여섯 개를 한 기기에서 통일해 찍는 편이
기기 테두리·상태바·모서리 반경이 어긋나지 않는다.

찍기 전에 정리할 것:

- **상태바** — 시간·배터리·통신사가 프레임마다 다르면 여섯 장이 따로 논다.
  방해금지 모드를 켜서 알림 배너가 끼어드는 사고를 막는다.
- **계정** — 개발용 계정으로 찍는다. 실제 이용자의 닉네임·프로필·연주가 화면에 뜨면
  그건 그 사람의 개인정보이자 초상이다. 랜딩은 공개 페이지라 동의 없이 쓸 수 없다.
  (같은 이유로 `../reel/` 의 스톡 영상도 얼굴 없는 클립만 골랐다 — 그쪽 SOURCES.md 참고)
- **길이** — 6초. 루프라 끝과 처음이 이어지므로, 스크롤을 멈춘 상태에서 시작하고
  같은 상태에서 끝내야 이음매가 튀지 않는다.

iOS 화면 기록(제어센터)으로 찍은 `.mov` 를 맥으로 옮겨 아래 규격으로 다시 인코딩한다.

## 인코딩

기기 칸은 세로 9:19.5다. 화면 기록은 이미 그 비율이라 자를 필요가 없다 — 크기만 줄인다.

**폭은 1040이다**(데스크톱 벌). 표시 폭(414 CSS px)만 보고 540 으로 잡았다가 흐릿하게
나왔다 — 맥은 devicePixelRatio 가 2라 실제로 필요한 건 **829 물리 픽셀**이고, 540 을
얹으면 1.54배 확대돼 글자 획이 뭉개진다. 900 으로 올렸더니 큰 화면에서 다시 1.16배
확대돼 뿌옜다. 그래서 1040 이다. **휴대폰 벌은 780 이다** — 아래 「두 벌로 낸다」.

```sh
ffmpeg -i 원본.mov -ss 0 -t 6 \
  -an -vf "scale=1040:-2,fps=24" \
  -c:v libx264 -profile:v main -pix_fmt yuvj420p -crf 30 -preset slow \
  -movflags +faststart  feed.mp4
```

- `-an` — 무음이어야 한다. 소리가 있으면 iOS 가 자동재생을 막는다.
- `+faststart` — 헤더를 앞으로 보낸다. 없으면 파일을 끝까지 받아야 첫 프레임이 뜬다.
- `-pix_fmt yuvj420p` — 화면 기록이 full range(`color_range=pc`)다. `yuv420p` 로 내보내면
  색이 limited range 로 눌려 배경이 밝아진다.
- `-crf 30` — 1040폭에서 이 값이 균형점이다. 28은 눈에 띄게 낫지 않으면서 25% 무거워진다.

**한 파일이 900KB를 넘으면 다시 줄인다.** 화면에 들어올 때 받으므로(지연 로드)
첫 화면 무게에는 들어가지 않지만, 그 장에 닿는 순간의 대기가 길어진다.
잇츠 세 파일이 상한에 가까운 이유는 아래에 적었다.

### 스크롤로 넘기는 화면(스크럽)은 따로 잡는다

`next/index.html` 에서 `data-scrub` 이 붙은 슬롯은 재생하지 않고 스크롤에 맞춰
프레임을 고른다. seek 이 잦으므로 키프레임을 촘촘히 넣어야 한다.

```sh
ffmpeg -i 원본.mov -an -vf "scale=1040:-2,fps=24" \
  -c:v libx264 -profile:v main -pix_fmt yuvj420p -crf 28 -preset slow \
  -g 4 -keyint_min 4 -sc_threshold 0 -movflags +faststart  pick.mp4
```

`-g 4` 는 4프레임마다 키프레임이다(85프레임에 22개). 모든 프레임을 키프레임으로(`-g 1`)
하면 seek 이 가장 정확하지만 파일이 2배가 된다. `-g 12` 는 8개뿐이라 눈에 띄게 거칠다.

스크럽 슬롯은 마크업에 `src` 를 직접 두고 `preload="auto"` 로 받는다 —
지연 로드로는 `duration` 이 잡히지 않아 스크롤 계산이 그대로 되돌아 나간다.
지연 로드를 쓰려면 `preload` 를 `src` 보다 **먼저** 올려야 한다. 순서가 반대면
브라우저는 아무것도 받지 않는다(`data-swipe` 슬롯이 그 방식이다).

### 재생 사이에 스크롤로 넘기는 화면(`data-bridge`)

잇츠 장이 그렇다. 멈춰 있으면 지금 잇츠가 돌고, 스크롤하면 다음 잇츠로 넘어간다.
**파일 셋이다** — 앞 잇츠(재생) · 넘김(스크롤) · 뒷 잇츠(재생).

```
its-a.mp4      16.1초  1877KB   앞 잇츠, loop
its-swipe.mp4   2.2초  1133KB   넘김, 60fps 134프레임, 스크롤이 프레임을 고른다
its-b.mp4      15.8초  1719KB   뒷 잇츠, loop
```

마크업은 `data-bridge="3"` 과 `data-fps="60"` 뿐이다 — 마디 3 의 뒤 40% 에서만
두 잇츠 위에 얹힌다. `data-fps` 는 seek 을 끊어 넣을 격자이며 파일의 프레임률과
같아야 한다.

**넘김을 CSS 로 흉내 내지 않는다.** 영상 두 장을 세로로 밀면 상단바와 탭바까지
같이 밀려 올라간다 — 앱에서 그것들은 제자리에 남는다. 실제 녹화를 쓰는 이유가 그것이다.

#### 자를 때는 앞에서부터만 자른다

받은 세 파일을 그대로 쓰되, 길이만 정해진 만큼 줄인다. 배속·프레임 재선택은
하지 않는다 — 촬영한 사람이 고른 구간이 곧 보여줄 구간이다.
지금은 앞·뒷을 각각 절반으로 줄였다(30초 → 16초, 합 8.2MB → 4.7MB).

**반드시 0초부터 자른다.** 세 파일이 한 촬영을 자른 것이라
**넘김의 마지막 프레임이 곧 뒷 잇츠의 첫 프레임**이다(실측 차이 2.17).
뒷 잇츠를 가운데부터 잘라 쓰면 이 연결이 깨지고, 도착하는 순간 연주가 딴 데로 튄다.
실제로 3초 지점부터 잘랐다가 차이가 29.69 로 벌어졌고 눈에 그대로 보였다.

다만 재생 쪽 슬롯은 `loop` 라, 넘기는 동안 다음 잇츠를 **첫 프레임에 세워 둬야**
한다. 앞서 돌던 자리에서 이어받으면 이어진 것이 무의미해진다(스크립트가 맡는다).

#### 프레임 수를 아끼지 않는다

스크롤 값을 그대로 시각에 넣으면 안 된다. 트랙패드 한 번이 스크롤을 600px 씩
건너뛰므로 **프레임 두어 장만 그려지고** 넘김이 통째로 사라진다(실측).
목표값으로 프레임마다 다가가게 하면 21프레임이 380ms 에 걸쳐 그려진다.

그래서 파일의 프레임 수가 곧 천천히 스크롤할 때의 매끄러움이다.
넘김만 60fps 로 두는 이유가 그것이다.

#### 로컬 미리보기 서버는 Range 를 지원해야 한다

`python3 -m http.server` 는 HTTP Range 를 무시한다. 그러면 브라우저가 seek 을
포기해 `video.seekable` 이 비고, **스크럽과 넘김이 통째로 죽는다**(파일은 멀쩡한데
`currentTime` 이 0 에서 움직이지 않는다). GitHub Pages 는 Range 를 지원하므로
배포본에는 없는 문제지만, 미리보기에서 「스크롤해도 안 넘어간다」가 보이면
이것부터 의심한다.

#### 이 셋은 여전히 크다

앞·뒷이 각각 1.8MB 대다(반으로 줄인 뒤). 세 칸에서 카메라 영상이 동시에 도는
화면이라 같은 CRF 에서 다른 화면의 3~5배가 나온다. 지연 로드라 첫 화면 무게에는
들어가지 않지만 그 장에 닿는 순간의 대기가 있다. 더 줄여야 하면:
길이를 더 줄이거나(0초부터), CRF 36 으로 올리거나(화질 손해가 눈에 띈다),
폭을 원본 604 로 내린다.

#### 원본 화질 — 잇츠 세 파일은 절반 해상도다

받은 원본이 604×1314 다. 필요한 폭은 828(414 CSS px × DPR 2)이므로 1.4배 확대해
넣었다. 다시 받을 수 있다면 **원본 해상도(1206×2622)** 녹화로 갈아야 한다.
`grid.mp4` 는 원본 해상도로 받아 그대로 썼다.


### 두 벌로 낸다 — 1040폭과 780폭

기기 칸이 화면마다 다르다.

```
휴대폰    283 CSS px × DPR 3 = 849 실제 px   →  780폭
태블릿    371 CSS px × DPR 2 = 742 실제 px   →  780폭
데스크톱  458 CSS px × DPR 2 = 916 실제 px   →  1040폭
```

**벌을 가르는 선은 픽셀 수가 아니라 화면 종류다**(`pickSrc`). 픽셀만 보면 1440 노트북의
기기 칸(738 실제 px)이 프로 맥스의 칸(849)보다 **작아서**, 실수요로만 가르면 노트북이
휴대폰 벌을 받는다 — 지금까지 보던 것보다 흐려진다. 그래서 860px 경계(CSS)로 가르고,
휴대폰 쪽에서만 실수요 880 을 넘는지 한 번 더 본다.

**재는 것은 기기 상자가 아니라 화면 칸이다.** CSS 로 그린 테는 5px 이라 상자와 화면이
사실상 같았고, 그래서 `.dev` 를 재고 있었다. 프레임이 그림으로 바뀌면서 상자가 화면보다
9% 커졌는데 그대로 뒀더니 휴대폰이 페이지 내내 1040 벌을 받았다.

```
.dev     재기   308 × DPR 3 = 924 실제 px  > 880  →  1040 벌   전체 11.9MB
.dev__scr 재기  281 × DPR 3 = 843 실제 px  ≤ 880  →   780 벌   전체  6.0MB
```

영상이 채우는 것은 상자가 아니라 **구멍**이다. `<img srcset>` 의 `sizes` 도 같은 이유로
구멍 폭이어야 한다 — 첫 화면 사진을 꽉 채우던 시절의 `100vw` 를 그대로 뒀더니 배율 2
기기에도 1040 벌이 갔다.

#### 휴대폰 벌은 540 이 아니라 780 이다 — 해상도가 CRF 를 이긴다

기기를 키우면서 540 벌이 1.5배 확대돼 뿌예졌다. 그렇다고 1040 벌을 보내면 한 장에
1~3MB 다. 그래서 중간 벌을 뜨되 **CRF 를 낮추는 대신 해상도를 올렸다.**

```
its-a.mp4   540폭 CRF 30   961KB   ← 예전 휴대폰 벌
            780폭 CRF 34  1019KB   ← 지금. 크기가 같은데 눈에 띄게 또렷하다
           1040폭 CRF 30  2714KB   ← 데스크톱 벌
```

작은 벌은 **원본에서 뜨는 것이 원칙이다.** 다만 자른 지점이 문서에 남아 있는 것만
그렇게 한다 — 잇츠 셋(앞 16.2초 · 뒷 15.867초 · 넘김 전체)이 그렇다. 나머지
(record · pick · grid · tour-t)는 자른 지점이 남아 있지 않으므로 **1040 벌을 0.75배로
줄여** 뜬다. 다시 자르면 프레임이 어긋나고, 그 어긋남은 이음매에서 그대로 보인다.
이중 압축을 상쇄하려고 그쪽만 CRF 를 한 단계 낮춘다(32, 스크럽은 30).

### 멈춰 있는 화면은 사진으로 둔다

탭바로 열리는 네 화면(홈 · 스페이스 · 랭킹 · 마이페이지)은 그 자리에서 아무것도
움직이지 않는다. 영상으로 두면 같은 그림에 프레임만 쓴다. 정지 여부는 **실효
프레임률**로 안다 — 정지 화면이면 인코더가 중복 프레임을 버린다.

```
정지 화면 녹화    322프레임 / 13.7초 = 23.5 fps
연주가 도는 화면  1944프레임 / 32.4초 = 60.0 fps
```

재는 법 — **`-fps_mode passthrough`**. 전환이 5프레임뿐이라 스크럽할 수 없다고 두 번
잘못 말했는데, 프레임을 뽑을 때 중복이 버려져 그렇게 보였을 뿐이다.

**넘어가는 순간은 영상이다.** 앱의 탭 전환은 60fps 로 9~16프레임이라 스크롤에 매달 수
있다. 사진 두 장을 겹치는 것으로도 재현되지만(혼합비가 고르게 떨어진다), 실제 녹화를
쓰는 편이 손끝에 붙는다.

### 다음 화면이 자라 나오는 자리(`data-expand`)

`grid.mp4` 의 프리뷰 창에서 잇츠가 자라 나온다(지니의 반대). 창의 자리를
마크업에 적어 둔다 — `data-window="위 오른 아래 왼 반경"`, 단위는 %.

```
data-window="13.50 7.22 16.67 7.22 3.56"
```

실측으로 잡는다. 배경이 흰색이므로 「흰색 아닌 픽셀」의 경계를 훑으면
`x 65~834, y 264~1629` 가 나오고, 모서리 반경은 왼쪽 경계가 안정되는 y 까지의
거리(32px)다. 눈으로 어림하면 몇 px 이 어긋나고, 그 어긋남이 그대로
「창이 자리에서 살짝 벗어나 자란다」로 보인다.

## 정면 기기도 렌더 목업 그림이다 (`front.png`)

「어떻게」·「기능」 장과 휴대폰 히어로에 서는 반듯한 기기는 CSS 로 그린 검은 모서리
사각형이었다. 이제 렌더 목업 그림을 얹는다 — 옆면 레일과 버튼, 두께가 다 보인다.

받은 파일은 흰 바탕에 흰 화면(904×1780)이다. 뚫는 순서는 기울인 목업과 같다.

1. 바깥과 화면에서 각각 **범람 채우기** → 알파 0. 둘은 검은 테가 막고 있어 안 샌다.
2. 불투명 덩어리 중 **가장 큰 것만** 남긴다. 이 한 줄이 **그림에 그려진 다이내믹
   아일랜드**를 지운다 — 녹화가 제 아일랜드를 갖고 있어서, 남기면 검은 혹이 둘이 된다.
   (워터마크가 있는 파일이면 화면 위 글자도 같이 빠진다. 기기 몸통에 걸친 자국은
   레일이 세로로 균일하다는 점을 이용해 세로 중앙값으로 덮었다.)
3. 가장자리 알파 매팅 — 흰 바탕과 섞인 경계 픽셀의 α 를 되돌린다. 이걸 빼면
   기기 윤곽에 **흰 실선**이 남는다.
4. 색 16단계 양자화 + 기기 상자에 맞춰 자르기 → **823×1689, 45KB**.

```
구멍   좌 4.617%  상 1.895%  폭 90.887%  높이 96.211%   (상자 823×1689 기준)
비율   2.172 — 녹화(2.174)와 사실상 같다. 잘리는 곳이 없다
```

### 자르는 일은 프레임 그림에 맡긴다 — 단, 크기는 구멍 그대로

처음에는 화면을 구멍 자리에 딱 맞추고 CSS `border-radius` 로 잘랐다. 그랬더니
귀퉁이마다 얇은 틈이 보였다 — **프레임의 구멍은 애플식 연속 곡률(스쿼클)이고
`border-radius` 는 타원이라**, 반경을 같게 맞춰도 곡선이 어긋난다.

그래서 화면을 구멍보다 3.3% 크게 깔아 봤다. 귀퉁이는 깨끗해졌지만 **화면이
확대됐다** — `object-fit:cover` 가 넘치는 만큼 잘라내서 위아래 2%, 상태바(9:41)와
탭바가 먹혔다. 「배치가 엉성해졌다 · 좀 확대된 화면이야」가 이것이다.

답은 **크기는 구멍과 같게, 반경만 구멍보다 작게** 다.

```css
.dev__scr{left:4.4%;top:1.8%;width:91.3%;height:96.6%;border-radius:12%/5.5%}
```

- 곧은 변은 구멍과 정확히 겹친다 → 확대도 잘림도 없다.
- 반경이 작아 귀퉁이만 구멍 밖(테)으로 나가고, 거기만 그림에 덮인다.
- 구멍 실측은 좌 4.617 / 상 1.895 / 폭 90.887 / 높이 96.211 %. 0.2%p 쯤 키운 것은
  기기 폭이 소수점일 때 생기는 반 픽셀 틈을 메우기 위한 것이다.
- 그림은 `.dev::after` 로 얹으므로 **마크업을 하나도 안 건드린다.**
- 그림자는 상자가 아니라 기기 모양을 따라야 하므로 `filter:drop-shadow` 를 쓴다.
- 첫 화면(휴대폰)의 「덮는 셈」도 상자가 아니라 **화면 칸**(0.913 × 0.966)으로 한다.
  테는 그림이라 배율과 함께 커지므로 상자로 재면 화면이 뷰포트를 못 덮는다.
  꽉 찬 동안에는 프레임 그림을 진행도만큼만 띄운다(`opacity:var(--t)`).

### 붙박이 판은 헤더 높이를 비켜 앉는다

프레임을 바꾸면서 `--dev-w` 를 45dvh 로 올렸더니 1440×900 에서 상자 높이가 831px 이
됐다. 판은 기기를 **100dvh 한가운데**에 놓는데 헤더(61px)는 그 위를 덮는 sticky 라,
기기 윗머리가 헤더 밑으로 **27px** 들어가고 아래는 34px 만 남았다 — 가운데도 아니고
여백도 없다. 이게 「배치가 엉성해졌다」의 나머지 절반이다.

```css
:root{--bar:61px}                    /* 13 패딩×2 + 로고 34 + 실선 1 */
.seq__pin{height:100dvh;padding-top:var(--bar);align-content:center}
.seq{--dev-w:min(520px,72vw,calc((100dvh - var(--bar) - 96px) / 2.052))}
```

절대 dvh 를 상한으로 쓰면 화면 높이마다 여백이 제멋대로가 된다. 「헤더 아래 남은
높이 − 위아래 48px」로 재면 900 에서도 1080 에서도 위아래가 정확히 48px 이다.
휴대폰은 `--bar` 를 50px 로 덮어쓰므로 같은 식이 그대로 산다.

**파일을 갈아 끼울 때** 다시 재야 하는 값은 넷이다 — 상자 크기(`aspect-ratio`),
구멍의 좌·상·폭·높이(%), `--dev-w` 식의 비율(2.052), 그리고 첫 화면 셈에 쓰는
폭·높이 비율(0.913 · 0.966).

## 휴대폰 첫 화면 — 제목 하나가 화면 가운데 선다

여기가 두 번 바뀌었다. 남겨 둔다 — 두 번 다 「더 보여 주려다 덜 전해진」 경우다.

**1차. 앱 홈 화면이 뷰포트를 꽉 채운다.** 스크롤하면 줄어들며 기기 안으로 들어갔다.
셋이 잘못됐다. ① 첫 화면에 말이 하나도 없어서 후킹이 아니라 「이게 뭐지 · 페이지가
깨졌나」로 읽힌다(스크린샷 안의 「♪ JAMIT」이 우리 헤더처럼 보여 더 헷갈린다).
② 줄어드는 중간에 우리 헤더가 앱 상태바(9:41)와 겹쳐 헤더가 둘로 보이고, 제목은
줄어드는 기기 **뒤에서** 올라와 가려진다. ③ 200dvh 를 쓰는데 그 동안 전달되는 정보가 0.

**2차. 글이 먼저 오고 앱 화면이 화면 끝에 걸친다.** 말은 생겼지만 좁은 화면에 기기까지
세우니 제목이 위쪽에 몰려 작아 보였다.

**지금. 앱 화면이 아예 없다.** `brandnew.daangn.com` 이 그 자리를 어떻게 쓰는지 재 보니
제목 하나가 화면 한가운데 서고 아래에 「아래로 내려보세요」와 꺾쇠뿐이다. 앱 화면은
바로 다음 장부터 계속 나오므로 여기서 미리 보여 줄 이유가 없다. **데스크톱은 그대로다**
(기울인 두 대 · 왼쪽 정렬).

### 「아래로 내려보세요」

화면에 제목밖에 없으면 「여기가 끝인가」로 읽힐 수 있다. 걸친 기기가 하던 「아래에 더
있다」를 이 꺾쇠가 대신한다. 값은 당근 첫 화면에서 화소 단위로 잰 것이다(390×844).

```
글자   14px · 600 · rgb(175,175,176) · 가운데 (x 134~249, 폭 116)
꺾쇠   40×16px · 획 4px · rgb(85,86,91) — 글자보다 훨씬 짙다
사이   18px,  꺾쇠 밑에서 화면 끝까지 45px
둘 다 가운데 x=191.5 — 뷰포트 절반과 정확히 같다
```

색만 우리 palette 로 옮겼다. 당근은 흰 바탕이고 우리는 회색 종이(#ecedf1)라 같은
`#AFAFB0` 을 쓰면 더 흐려진다 — 먹을 34% 로 깔면 종이 위에서 같은 밝기가 된다.

### 제목만 남긴다

기기가 빠지면서 자리가 남았으므로 제목을 그 급으로 키웠다 —
`clamp(38px, 11.5vw, 54px)`. 11.5vw 는 가장 긴 줄(「나만의 연주가」 6글자 + 사이)이
좌우 여백 안에 드는 값이다(390 → 45px, 375 → 43px, 430 → 49px, 상한 54).
**데스크톱의 `--t-hero` 는 건드리지 않았다.**

리드(「각자의 파트만 연주해서 올리면 …」)는 휴대폰에서만 걷었다 — 좁은 화면에서는
제목 하나가 더 세게 읽히고, 같은 말을 바로 다음 장(「혼자 녹화한 연주가 합주가
되기까지」)이 이어서 한다. 데스크톱에는 그대로 둔다: 거기는 제목 옆이 비어 있지 않고
(기울인 두 대) 왼쪽 정렬이라 리드가 제목을 받쳐 준다.

### 「iOS · Android」는 거짓말이었다

앱스토어만 열려 있고 플레이 스토어 링크가 없다. 배지 아래를 **「Android 준비 중」**으로
고쳤다 — 이건 사실 문제라 데스크톱도 같이 고쳤다.

### 스티커 셋은 넣었다 뺐다

제목만 남기고 나니 위아래가 비어 보여, 악기 · 헤드폰 · LP 를 종이 스티커처럼 흩어 봤다
(따내고 · 얹고 · 떠다니게 하고 · 판은 돌렸다). **결국 뺐다** — 당근이 그 자리를 제목
하나로만 쓰는 것이 결국 더 세다는 판단이다. 그림 셋도 지웠다.

남길 만한 것 둘.

1. **`display:none` 이어도 그림은 받는다.** 데스크톱에서 스티커 판이 통째로
   `display:none` 인데 첫 화면에서 68KB 를 헛으로 받고 있었다(실측).
   `<picture><source media>` 로 빈 그림을 줘야 요청이 안 나간다 — 이 페이지가 히어로의
   기울인 두 대와 첫 화면 사진에서 이미 쓰는 수법이고, **새로 그림을 얹을 때마다
   다시 확인해야 하는 자리**다.
2. **알파 매팅의 부호는 배경이 밝다는 보장이 없다.** 레코드 그림은 배경이 어두운
   체크무늬(≈68)라 경계(흰 종이)보다 어두웠다. 안쪽 이웃 중 「가장 짙은 것」을
   전경으로 고르면 알파가 거꾸로 나온다 — **배경 밝기에서 가장 먼 것**을 골라야 한다.
   `scratchpad/key.py` 에 그렇게 고쳐 두었다.

### 첫 장은 「헤더를 뺀 한 화면」이다

`min-height:100dvh` 로 두면 sticky 헤더가 **흐름에서 차지한** 50px 만큼 아래가 잘려,
화면 밑에 붙인 꺾쇠가 접힌 자리로 내려간다. `calc(100dvh - var(--bar))` 로 잡고
위 칸(`1fr`)에 글을 가운데, 아래 칸(`auto`)에 꺾쇠를 붙인다.

```
390×844   글 261~560 (가운데 x 195 = 뷰 절반)   꺾쇠 아래에서 45px
375×667   글 169~469 (가운데 x 188 = 뷰 절반)   꺾쇠 아래에서 45px
```

앱 화면이 빠지면서 첫 화면 무게도 200KB 줄었다(`tour-home.jpg` 를 안 받는다).

## 휴대폰 — 판은 못 박은 채로, 글만 한 줄씩

휴대폰에서도 **전환 넷(지니 · 확대 · 잇츠 넘김 · 크로스페이드)이 그대로 산다.**
이 페이지에서 그 넷은 장식이 아니라 「앱이 이렇게 움직인다」는 내용 자체이기 때문이다.

문제는 자리였다. 화면 한 장(852px)에 기기와 아코디언 다섯 줄을 같이 세우면 기기가
162px 로 쪼그라들고 그러고도 넘쳤다(667px 짜리 화면에서 168px 이 잘렸다). 한때 토스처럼
판을 풀어 카드로 세워 봤는데, 그러면 스크롤이 프레임을 고르는 자리가 통째로 사라진다.

그래서 반대로 잘랐다 — **닫힌 줄을 감춘다.** 어차피 열린 줄 하나만 읽는 짜임이라
잃는 것이 없고, 글이 145px 로 줄어 판이 그대로 선다.

```
             기기   글    상단바   사이   합계   화면
아이폰 15     622    152     50      20    844    852
아이폰 SE     438    152     50      20    660    667
```

- **판 제목(「혼자 녹화한 연주가 합주가 되기까지」)도 뺀다.** 좁은 화면에서 두 줄을
  차지하는데, 줄 제목(녹화 · 트랙 조합 …)이 이미 지금 무엇을 보는지 말해 준다.
  그렇게 번 자리를 전부 기기에 준다 — 162 → 275px 이다.
- 기기 폭은 세 값 중 가장 작은 것이다 — `min(290px, 76vw, (100dvh - 212px) / 2.167)`.
  - `290px` — 배율 3배에서 870 실제 px 이라 780 벌 안이다(위 참고).
  - `76vw` — 좁은 기기에서 가로가 먼저 막힌다.
  - 셋째 값이 **「글이 쓰고 남은 높이」** 다. 기기 높이는 폭의 2.167배(9:19.5)이므로
    화면 높이에서 글·상단바가 쓰는 212px(상단바 50 + 글 118 + 사이 20 + 여유 24)을
    빼고 그 비율로 나눈다. 이게 없으면 작은 화면과 눕힌 태블릿에서 아래가 잘린다.

```
기기 폭   아이폰 SE 210 · 갤럭시 271 · 아이폰 15 290 · 프로 맥스 290 · 아이패드 415
```

### 상단바 높이는 값 하나로 못 박는다

판과 히어로가 **상단바만큼 자리를 비워 둔다**(`padding-top:var(--bar)`). 둘이 어긋나면
기기 윗머리가 잘린다 — 50 으로 보고 비웠는데 상단바가 66px 이어서 「합주 모집」에서
9px 이 가려졌다. 66이었던 이유는 로고 링크의 누름 영역(44px)이 줄 높이를 밀어 올려서다.

```css
:root{--bar:50px}
.top__in{padding:0;min-height:calc(var(--bar) - 1px)}
.top__id{padding:8px 0;margin:-8px 0}   /* 누름 영역은 44px, 줄 높이에서는 뺀다 */
.seq__pin,.hero{padding-top:var(--bar)}
```

「여유 24」도 이 때문이다. 판이 가운데 정렬이라 그 절반이 상단바와 기기 사이의 틈이
된다 — 8 로 뒀을 때는 4px 밖에 남지 않아, 글꼴이 조금만 크게 잡혀도 다시 닿았다.
지금은 21px 이 남는다(기능 장 기준, 아코디언 장은 26px).
- 붙박이 판에 `padding-top:56px` 을 준다. 없으면 작은 화면에서 기기 윗머리가
  상단바에 가린다(실측: 667 화면에서 기기 윗변이 5px 이었다).
- 줄마다 글 높이가 다르면(3줄 · 2줄) 그만큼 기기가 들썩인다. 가장 큰 줄에 맞춰
  자리를 미리 잡아 둔다 — `.acc__list{min-height:108px}`, `.feat{min-height:118px}`.
  실측 흔들림 62px → 0~1px.
- **데스크톱에서 블록 사이를 벌리던 여백(`.feat__row + .feat__row`)은 지운다.**
  휴대폰에서는 한 번에 한 블록만 보이는데도 둘째부터는 그 여백을 이고 있어서,
  첫 블록만 34px 위에 앉아 있었다. 지우고 나니 네 블록의 이름표가 같은 자리에 선다
  (실측: 넷 다 691px). 덤으로 글칸이 152 → 118px 로 줄어 기기가 10px 커졌다.
- **「둘러보기」 줄의 알약(앱 다운로드)은 휴대폰에서 뺀다.** 그 줄 하나 때문에 다섯 줄
  모두가 62px 씩 자리를 비워 두게 되고, 그만큼 기기가 작아진다. 내려받을 곳은
  상단바 배지와 맨 아래 장에 이미 있다. 데스크톱에는 그대로 둔다 — 거기서는
  높이가 남는다.
- 그래서 지금 기기 크기를 정하는 것은 아코디언이 아니라 **기능 블록**이다(152px).
  이름표 · 두 줄 제목 · 설명 셋이 들어가기 때문이다.
- 닫힌 줄을 감췄으므로 제목은 더 이상 누를 것이 아니다. 스크립트가 `button` 을
  `h3` 으로 바꾼다(읽기 프로그램에 「접힘/펼침」을 알리지 않는다).

### 지연 로드의 눈금은 화면이 아니라 마디다

붙박이 판에서는 화면 여섯 장이 기기 한 대에 겹쳐 있어 **상자가 전부 같은 자리다.**
`.shot` 을 그대로 관찰하면 판이 가까워지는 순간 여섯이 한꺼번에 나간다.

```
.shot 을 눈금으로   첫 화면 2034KB  (넘김 583 + 녹화 425 + 스크럽 343 이 미리 나간다)
.beat 을 눈금으로   첫 화면  901KB  (녹화 425 + 글꼴 331 + 포스터 50)
```

마디는 한 화면씩 떨어져 있으므로 읽는 순서대로 하나씩 받는다. 데스크톱도 같이
가벼워진다(첫 화면 1.6MB). 넘김 장은 제 마디의 뒤쪽에서 쓰이므로 같은 마디를 본다.

```
휴대폰(390×844) 실측   첫 화면 1244KB · 끝까지 훑으면 5985KB · 404 없음 · 가로 넘침 0
                      1244 중 552 는 다음 장(녹화) 미리 받기다 — 첫 그림에 꼭 필요한
                      것은 html 108 + 글꼴 331 + tour-home 200 + front 45 = 684KB
데스크톱(1440×900)     첫 화면 2235KB · 끝까지 12749KB
```

## 앱 UI 를 페이지 위로 들어 올린다 (`#detail`)

toss.im 은 제 앱의 카드를 기기 밖으로 꺼내 부드러운 바탕 위에 세운다. 같은 짜임으로
셋을 올렸다 — 유튜브 구간 고르기 · 녹음 싱크 측정 · 업적 축하. 앱의 흐름 순서다
(준비 → 녹화 전 → 올린 뒤).

**둘은 스크린샷이 아니라 다시 그린 것이다.** 값은 전부 `JamIT-iOS` 소스에서 그대로 왔다.

| 옮긴 것 | 원본 |
|---|---|
| 싱크 조율 패널 | `apple/JamIT/Recording/CalibrationOverlay.swift` |
| 업적 축하 카드 | `apple/JamIT/Core/UI/AchievementToast.swift` |
| 판(LP) | `apple/JamIT/Core/UI/AchievementVinyl.swift` |
| 색 · 여백 · 글자 | `apple/JamIT/Theme/AppColor.swift` · `AppTypography.swift` |

그림으로 뜨면 배율마다 뿌옇고 안무도 못 살린다. 다시 그리면 어느 화면에서도 또렷하고,
스크롤에 맞춰 실제 안무가 논다. 길이는 **전부 `--u` 곱이다** — `--u` 는 「iOS 1pt 이
웹에서 몇 px 인가」라, 소스의 숫자(56 · 176 · 185 · 18 · 2.5 …)를 그대로 적어 둘 수 있다.
앱이 값을 고치면 여기도 그 한 줄만 고친다.

### 스프링은 `linear()` 로 푼다

SwiftUI `.spring(response:dampingFraction:)` 은 감쇠 진동이다. cubic-bezier 로는
**넘겼다 돌아오는 되튐**이 안 나온다(단조 증가만 표현한다). 식을 그대로 풀어 적었다.

```
x(t) = 1 − e^(−ζω₀t)(cos ω_d t + (ζω₀/ω_d) sin ω_d t)
ω₀ = 2π/response,  ω_d = ω₀√(1−ζ²),  실질 지속 ≈ 7/(ζω₀)
```

- 등장 `spring(0.36, 0.70)` → 573ms, 최대 4.6% 넘긴다 → `--sp-in`
- 열림 `spring(0.50, 0.86)` → 648ms, 최대 0.5% 넘긴다 → `--sp-open`

시간표는 소스의 `choreograph()` 그대로다.

```
0            원(56)이 튄다            spring(0.36, 0.70)
0.3 → 1.0    앰버 선이 한 바퀴 돈다    easeInOut 0.7
1.0          선을 **먼저** 지운다      easeOut 0.16
1.0 → 1.65   카드(176×185)로 열린다   spring(0.50, 0.86)
1.0 → 2.5    판이 한 바퀴 돈다        easeOut 1.5
```

선을 먼저 지우는 것은 소스의 `sweepRing` 주석에 적힌 이유 그대로다 — 카드가 커질 때
링이 남아 있으면 176pt 짜리로 **함께 부푼다**. 앱은 3.2초 뒤 스스로 닫히지만 페이지에서는
열린 채로 둔다. 닫히면 빈 바탕만 남아 늦게 스크롤한 사람이 아무것도 못 본다.

### 싱크 조율도 「측정 시작」을 누른 뒤가 논다

회차 수와 간격은 앱의 상수 그대로다(`Recording/SyncCalibration.swift`).

```
probeCount 3 × 엔진 둘(웹 · 그룹) = probeTotal 6
captureSettleMs 500   녹음이 확실히 돈 뒤 첫 삑까지의 여유
probeGapMs     700    회차 간격
```

그래서 페이지에서도 **5초쯤 걸린다.** 줄이고 싶었지만 줄이면 화면에 적힌
「신호음이 6번 울려요」가 거짓말이 된다. 단계는 앱의 `SyncCalibrator.phase` 그대로다.

```
idle   측정 시작 / 녹화 그만두기
run    진행바(앰버) + 「측정 중 · n/6」 + 측정 중단
done   측정 완료 + 완료 + 다시 측정
```

`done` 이 되면 준비 안내(「대 주세요」 · 그림 · 「6번 울려요」)와 「아직 측정 전」이 접힌다 —
소스의 `phase != .done` · `storedMs == nil` 분기 그대로다. **그래서 패널 높이가 단계마다
다르다**(347 → 329 → 258px). `height:auto` 는 전환이 안 걸리므로 두 높이를 재서 실제 px 으로
옮긴다. 끝나면 `idle` 로 되돌린다 — `done` 에 세워 두면 준비 안내가 접힌 채로 남아,
늦게 스크롤한 사람에게 **가장 덜 알려 주는 화면**이 서 있게 된다.

**삑이 울리는 순간의 파형 튀김은 앱에 없는 것이다.** 소리가 안 나는 페이지에서 「여섯 번
울린다」를 눈으로 말할 방법이 이것뿐이라 더했다. 그 밖에는 앱에 없는 움직임을 넣지 않았다.

#### `void el.offsetWidth` 로는 SVG 애니메이션이 안 되감긴다

클래스를 지웠다 붙여 애니메이션을 다시 트는 그 관용구는 **HTMLElement 에서만 통한다.**
`offsetWidth` 는 SVG 요소에 없어서(undefined) 읽어도 스타일이 다시 계산되지 않고, 지우고
붙인 것이 한 덩어리로 묶인다.

```
실측: 삑 여섯 번 중 **첫 번째만** 울고 is-beep 이 붙은 채로 굳었다(animationstart 1건).
고친 뒤 6건.
```

되감으려면 `getBoundingClientRect()` 를 읽는다 — 이쪽은 SVG 에도 있고 스타일·레이아웃을
함께 흘린다.

### 리퀴드 글래스는 흰 면이 아니다

처음엔 `rgba(255,255,255,.72)` 로 채웠다. 뒤가 안 비쳐 그냥 흰 카드였다. 앱에서 이 카드는
`chromeGlass(overMedia: true)` — 유리다. 유리로 읽히게 하는 것은 셋이다.

1. **뒤가 보인다** — 알파를 0.2~0.5 로 낮추고 `backdrop-filter` 로 흐림·채도·밝기를 올린다.
   그러려면 **뒤에 굴절할 것이 있어야 한다.** 바탕을 옅은 회색 하나로 두면 아무리 투명해도
   유리인지 알 수 없어서, 바닥에 색 덩어리 셋을 깐 그라데이션을 두었다.
2. **윗면 정반사** — 위 가장자리의 밝은 실선 하나(유리 두께의 윗면이 빛을 받는 자리).
   아래에는 그보다 약한 되비침.
3. **가장자리가 밝다** — 안쪽으로 옅은 흰 번짐. 모서리에서 빛이 꺾여 테가 밝아 보이는 것.

### `♫` 는 글자로 두면 안 된다

앱의 `NoteGlyph` 는 `Text("♫")` 다. 이 페이지의 글꼴(MonoEn · Pretendard)에는 U+266B 가
없어 **마름모로 떨어진다.** 그래서 SVG 로 그렸다 — 크기는 앱과 같은 판 지름의 16% 다.

### 유튜브 구간 화면만 그림이다

셋 중 이 한 장만 다시 그리지 않았다. 안에 **실제 유튜브 영상 한 프레임**이 들어 있어
벡터로 옮길 수가 없다. 화면 캡처를 그대로 쓰되 테두리를 둥글려 다른 둘과 같은 카드로 세운다
(`tour-yt.jpg` 1040폭 97KB · `sm/` 780폭 66KB).

⚠️ **그 프레임은 남의 영상이다.** 공개 전에 우리 영상이나 권리가 있는 영상으로 갈아야 한다.

```
데스크톱(1440×900)  세 칸 · 카드 296 / 282 / 300px
1100~861            두 칸
860 이하            한 칸 — 위아래로 쌓인다(유튜브 → 싱크 → 업적)
```

### 눕힌 휴대폰이 유일하게 깨져 있었다

세워 든 화면 기준으로 짜 둔 규칙 둘이 거꾸로 놀았다.

```
844×390   꺾쇠가 화면 밖으로 밀렸다   — 제목 11.5vw = 97px 이 높이를 다 먹는다
844×390   붙박이 판의 기기가 87×178   — 「남은 높이 ÷ 2.052」인데 높이가 없다
780×360   같은 증상, 기기 72×148
```

고친 것 둘.

1. **제목이 세로 높이도 본다** — `min(clamp(38px,11.5vw,54px), 8.2vh)`.
   세워 든 화면에서는 8.2vh 가 늘 커서 아무 일도 하지 않는다(390×844 → 69px 대 45px).
2. **`max-height:560px` 에서 판을 두 칸으로 되돌린다** — 눕히면 폭이 800 넘게 남으므로
   데스크톱처럼 글 왼쪽 · 기기 오른쪽(뒤집은 판은 반대)으로 세우고, 기기는 높이만 본다.
   560 은 가장 큰 눕힌 휴대폰(Pro Max 가로 430)보다 넉넉히 위이면서 세워 든 가장 작은
   기기(SE 667)보다 아래인 값이다.

고친 뒤 844×390 의 기기는 146×300, 위아래 20px 씩이다.

### 601~860 은 카드가 두 칸이다

`#detail` 을 한 칸으로 두면 바탕만 넓어지고 카드가 그 안에 파묻힌다(아이패드 미니 세로:

## poster — 자동재생이 막힌 자리를 지킨다

iOS 저전력 모드는 무음 영상까지 막는다. 그때 화면에 남는 것이 poster이므로,
**poster 한 장만 봐도 무슨 화면인지 알 수 있어야 한다.** 스크롤 도중이나 전환 중간
프레임을 고르면 안 된다.

```sh
ffmpeg -i feed.mp4 -frames:v 1 -q:v 6 feed.jpg
```

webp 가 아니라 jpg다 — 이 기기의 ffmpeg 는 libwebp 없이 빌드돼 있고(`sips` 도 webp 출력을
지원하지 않는다) 억지로 맞출 이유가 없다. 100KB 안쪽이면 충분하다.

뽑은 뒤 `next/index.html` 의 해당 `<video>` 에 **`data-poster="../assets/app/feed.jpg"`** 를 넣는다.
`poster` 가 아니라 `data-poster` 인 이유가 둘이다.

- `poster` 는 `srcset` 이 없다. 마크업에 두면 화면 크기와 상관없이 1040 벌이 가고,
  스크립트가 나중에 `sm/` 으로 바꿔 봐야 이미 받은 뒤라 **두 장을 받는다**(실측:
  휴대폰 첫 화면 999KB 중 117KB 가 그 낭비였다).
- `poster` 는 지연 로드가 안 된다. 페이지를 열자마자 다섯 장이 한꺼번에 나간다.

`data-poster` 로 두면 영상과 같은 감시자가 화면 600px 앞에서 `poster` 를 달아 준다 —
그때 폭도 같이 고른다. 그래서 **poster 도 두 벌이 필요하다**: `sm/` 에 같은 이름으로
780폭을 둔다(`sips --resampleWidth 780 -s formatOptions 45`, 한 장 70~120KB).

```
첫 화면까지   999KB → 732KB
```

## 링크 카드(`og:image`)는 첫 화면을 렌더해서 뜬다

손으로 다시 짜지 않는다. **첫 화면이 바뀔 때마다 카드가 조용히 낡기 때문이다** —
앞의 카드가 그렇게 낡아서 넉 달 동안 「iOS · Android · 2026년 9월 출시 예정」과
옛 로고(막대 셋), 그리고 그 사이 바뀐 앱 UI 를 그대로 뿌리고 있었다.

뜨는 법(`scratchpad/og.mjs`) — 페이지를 1200×630 뷰포트에 띄우고 헤더 · 눈금 · 꺾쇠만
걷은 뒤, 등장 애니메이션(`.rise`)을 끝 상태로 고정하고 배율 2 로 찍는다.
받은 2400×1260 을 절반으로 줄여 JPEG 로 낸다.

- **가장자리에 걸치는 요소는 두지 않는다.** 링크 카드는 서비스마다 다른 비율로 잘라
  보여줘서, 일부러 걸친 것도 잘린 사고처럼 보인다. 실측 여백 85 / 124 / 68 / 68.
- **JPEG q:v 4 로 74KB.** q:v 2 는 106KB 인데 제목 글자에서 차이가 안 보인다.
- **주소에 `?v=2` 를 붙인다.** 카카오 · 페이스북 크롤러는 카드를 **주소 단위로** 오래
  들고 있어서, 파일만 갈아 끼우면 새로 공유해도 옛 카드가 나간다.

첫 화면을 크게 고치면 이 카드도 다시 떠야 한다.

## 계측 — 무엇까지 볼 수 있나

밖으로 나가는 것은 **Microsoft Clarity 하나뿐이다**(`y19bzkhlv6`). 나머지는 글꼴도
그림도 전부 같은 도메인에서 준다.

Clarity 는 세션 녹화 · 클릭/스크롤 히트맵 · 스크롤 깊이 · 브라우저/기기 · 리퍼러를
저절로 잡는다. 하지만 **「몇 번 눌렸나」를 숫자로 뽑으려면 이벤트를 직접 보내야 한다** —
특히 앱스토어 배지는 `target="_blank"` 바깥 링크라 눌리는 순간 다른 도메인으로 넘어가
자동 집계 대상이 아니다. 그래서 이 일곱을 보낸다.

```
appstore_click            배지 총계
appstore_click_header     헤더 배지
appstore_click_hero       첫 화면 배지
appstore_click_download   마지막 장 배지
contact_click             푸터 문의
reach_how / reach_more / reach_detail / reach_download    각 장 도달(장마다 한 번)
```

자리별 이름을 따로 두고 `clarity("set", …)` 태그를 안 쓰는 이유 — **`set` 은 세션
단위다.** 한 사람이 두 자리를 누르면 나중 것이 앞엣것을 덮어써 자리별 셈이 어긋난다.

「첫 화면에서 안 내려간 사람」은 따로 세지 않는다 — `reach_how` **가 없는 세션**이
그것이다. 이벤트를 하나 더 두면 같은 것을 두 번 세게 된다.

### 다운로드 수는 여기서 안 나온다

A(Clarity 이벤트)든 B(GA4)든 볼 수 있는 것은 **「배지를 눌렀다」까지다.** 그 순간
브라우저가 `apps.apple.com` 으로 넘어가면서 우리 스크립트는 끊기고, 거기서 실제로
받았는지는 남의 도메인 일이라 어떤 웹 분석으로도 못 본다.

다운로드 수는 **App Store Connect 「앱 분석」**에서 본다 — 웹 리퍼러 항목에 `jamit.kr`
이 뜨고 그 아래로 제품 페이지 조회수 → 다운로드 수가 나온다. 둘을 이어야 그림이 된다.

```
우리 페이지(Clarity)               App Store Connect
방문 → 어디까지 읽었나 → 배지 클릭   →   제품 페이지 조회 → 다운로드
```

### 처리방침과 어긋나면 안 된다

개인정보처리방침 제10조가 이미 Clarity 에 「방문 기록, 화면에서의 움직임(이동 · 클릭 ·
스크롤)」을 고지하고 있어 위 이벤트들은 **그 범위 안이다** — 개정하지 않았다.
**사람을 가릴 수 있는 값은 아무것도 싣지 않는다.** 이름표만 보낸다.

GA4 를 더한다면 그때는 처리방침 4차 개정이 따라붙는다 — 지금 웹사이트 항목(제6조 표 ·
제10조 · 제11조)에는 Clarity 만 적혀 있어서, 수집 주체 · 쿠키 · 보유 기간(14개월)을
새로 고지해야 한다.

    정면으로 어기는 행위다.
